# 产业园厂房销售认购系统 — 执行方案

> 技术栈：Spring Boot 3 + Vue 3 + MySQL 8 + Docker
> 目标：覆盖产业园厂房（标准厂房/独栋）从「房源 → 客户 → 认购 → 合同 → 审批 → 回款」的销售全流程，并支持合同审批对接 OA。

---

## 一、核心问题：合同审批是否要接入 OA？

### 1. 结论先行
**需要"审批流"，但不一定要接入外部 OA。**建议采用「系统内置审批流引擎 + OA 对接抽象层」的折中方案：

- MVP 阶段：用系统内置多级审批跑通业务闭环，自主可控、上线快。
- 后期阶段：通过预留的 `ApprovalGateway` 适配器接口，按需对接企业现有 OA（钉钉 / 企业微信 / 泛微 e-cology / 致远 A8 / 蓝凌等），业务代码无需改动。

### 2. 两种方案对比

| 维度 | 内置审批流 | 接入外部 OA |
|---|---|---|
| 上线速度 | 快 | 慢（需联调 OA 开放接口） |
| 自主可控 | 强 | 依赖 OA 厂商接口 |
| 审批入口 | 系统内 | 统一在 OA（员工习惯） |
| 与印章/归档/人事联动 | 需自建 | OA 已有 |
| 适用场景 | 无 OA / 希望业务闭环 | 已有成熟 OA 且要求集中审批 |

### 3. 为什么合同环节天然需要审批
厂房销售金额大、涉及法律与财务风险，合同从拟定到生效必须经过多方把关，典型审批链：

```
销售提交合同 → 销售经理(商务条款) → 财务(价格/回款/优惠) → 法务(合同条款/风险) → 分管领导(大额/特批) → 用印归档生效
```

任一节点驳回则退回修改。系统必须记录每个节点的审批人、意见、时间，形成可追溯的审批轨迹（审计 + 合规要求）。

### 4. OA 对接抽象设计（预留）
```
ApprovalGateway (接口)
 ├── InternalApprovalAdapter   // 内置审批流引擎（默认启用）
 └── OaApprovalAdapter         // 对接外部 OA（按需启用，配置化切换）
        ├── 发起：调用 OA 开放 API 创建审批实例，回传业务单号
        └── 回调/轮询：OA 审批结果同步回本系统，更新合同状态
```
通过配置 `approval.gateway=internal|oa` 切换，业务层只依赖 `ApprovalGateway` 接口，符合开闭原则。

## 二、业务全流程

```
1. 房源准备：录入产业园 → 楼栋 → 厂房单元（面积/单价/总价/状态）
2. 客户管理：登记意向客户（企业客户为主）、跟进记录
3. 认购：客户选房 → 销售创建认购单 → 锁定房源(状态=已认购) → 缴纳定金
4. 合同：基于认购单生成销售合同(价格/付款方式/优惠) → 提交审批
5. 审批：多级审批(内置或OA) → 通过则合同生效、房源状态=已签约
6. 回款：按付款计划登记定金/首付/分期/尾款回款
7. 交付与报表：房源状态=已售；销售看板/回款看板统计
```

### 房源状态机
`在售(ON_SALE) → 已认购(SUBSCRIBED) → 已签约(SIGNED) → 已售(SOLD)`
认购单取消 / 合同驳回作废时可回退到 `在售`。

### 合同/审批状态机
`草稿(DRAFT) → 审批中(APPROVING) → 已通过(APPROVED)/已驳回(REJECTED) → 已生效(EFFECTIVE)`

## 三、系统架构

```
浏览器 ──> Nginx(前端 Vue 静态资源 + /api 反向代理) ──> Spring Boot(REST API) ──> MySQL
                                                              │
                                                       ApprovalGateway
                                                       ├ Internal(内置)
                                                       └ OA Adapter(预留)
```

- 后端：Spring Boot 3 / Java 17 / MyBatis-Plus / Spring Security + JWT
- 前端：Vue 3 / Vite / Element Plus / Pinia / Vue Router / Axios
- 数据库：MySQL 8
- 部署：Docker Compose 一键编排（mysql + backend + frontend）

---

## 四、数据库设计（核心表）

| 表 | 说明 |
|---|---|
| `sys_user` | 用户（销售/经理/财务/法务/管理员） |
| `sys_role` | 角色，RBAC |
| `building_project` | 产业园项目 |
| `building` | 楼栋 |
| `factory_unit` | 厂房单元（房源，含面积/单价/总价/状态） |
| `customer` | 客户（企业客户） |
| `subscription` | 认购单 |
| `contract` | 销售合同 |
| `approval_flow` | 审批流实例 |
| `approval_task` | 审批节点任务（审批人/意见/结果/时间） |
| `payment_record` | 回款记录 |

详见 `db/init.sql`。

---

## 五、模块与接口

| 模块 | 主要接口 |
|---|---|
| 认证 | `POST /api/auth/login` 登录发 JWT |
| 房源 | `GET/POST/PUT /api/factory-units` 房源 CRUD、状态流转 |
| 客户 | `GET/POST/PUT /api/customers` |
| 认购 | `POST /api/subscriptions` 创建认购、`POST /api/subscriptions/{id}/cancel` |
| 合同 | `POST /api/contracts` 生成合同、`POST /api/contracts/{id}/submit` 提交审批 |
| 审批 | `GET /api/approvals/todo` 待办、`POST /api/approvals/{taskId}/approve|reject` |
| 回款 | `POST /api/payments` 登记回款 |
| 看板 | `GET /api/dashboard/summary` 销售/回款统计 |

---

## 六、部署与运行

```bash
docker compose up -d --build      # 一键启动 mysql + backend + frontend
# 前端: http://localhost:8088
# 后端: http://localhost:8080/api
# 默认账号: admin / admin123
```

`db/init.sql` 在 MySQL 容器首次启动时自动建表并插入演示数据（角色、用户、产业园、厂房、客户）。

---

## 七、迭代规划

- **第一期（本次 MVP）**：鉴权 + 房源 + 客户 + 认购 + 合同 + 内置审批流 + 回款 + 看板 + Docker。
- **第二期**：OA 适配器接入真实 OA、电子合同/电子签章、付款计划与逾期提醒。
- **第三期**：移动端（销售带看选房）、数据报表 BI、与财务/ERP 系统集成。
